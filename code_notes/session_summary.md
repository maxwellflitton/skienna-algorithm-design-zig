## Project layout

```
build.zig                     # generated by `zig init`
src/
  main.zig                    # executable
  root.zig                    # library entry point
  chapter_3.zig               # re-exports chapter 3's files
  chapter_3/
    linked_list.zig
    dictionary.zig
code_notes/
  testing.md                  # notes on testing in Zig
```

## Modules and imports

- Zig has no directory modules: there's no `mod.rs` or `__init__.py`.
  `@import` takes either a path to a `.zig` file or the name of a module
  registered in `build.zig`.
- Every `.zig` file is a struct. Its `pub` declarations are what other files can use.
- The convention is a file next to the folder that re-exports its contents:

```zig
// src/chapter_3.zig
pub const linked_list = @import("chapter_3/linked_list.zig");
pub const dictionary = @import("chapter_3/dictionary.zig");

// src/root.zig
pub const chapter_3 = @import("chapter_3.zig");
```

- Zig only compiles code that something uses. A broken declaration nothing
  refers to compiles without error. I hit this: `IntNode` had `next_ptr: ?*Node`,
  where `Node` was a generic function rather than a type, and it compiled until
  something used `IntNode`.

## Testing

Full notes are in `code_notes/testing.md`. The key points:

- `test "name" { ... }` is Zig's `#[test]`. There's no `#[cfg(test)]` module;
  tests sit next to the code and only compile when testing.
- Every check starts with `try`, e.g. `try std.testing.expectEqual(expected, actual)`.
- There are no setup or teardown hooks. Use a normal helper function for setup
  and `defer` for teardown.
- `std.testing.allocator` fails the run if memory leaks.
- `zig build test` only runs tests in files the test root uses, so each entry
  file includes:

```zig
test {
    @import("std").testing.refAllDecls(@This());
}
```

- `return error.SkipZigTest;` skips a test, like Rust's `#[ignore]`.
- `.?` unwraps an optional and panics on `null`, like `.unwrap()`.
- `zig build test --summary all` runs everything and prints the counts;
  `zig test file.zig --test-filter "name"` runs matching tests in one file.

## Documentation comments

- `///` documents the item below it and `//!` documents the file, as in Rust.
  Both use Markdown.
- A doc comment in a place that can't take one is a compile error, e.g. inside
  a function body. Use `//` there.
- Code blocks in doc comments are not compiled or run. Zig's version of a
  doctest is a test named after a declaration, `test next { ... }`, which the
  doc generator shows as that declaration's example.
- Generated docs only include `pub` declarations. To build them:
  `zig build-lib -femit-docs src/root.zig`, then serve the `docs/` folder over
  HTTP, e.g. `python3 -m http.server -d docs`.
- There's no `@param` tag or `# Arguments` section. Arguments are named in
  backticks in the description, e.g. "Inserts `insert_val` after `node`."
- Standard-library style is short plain sentences: "Caller owns the returned
  memory.", "Asserts that the list is not empty.", "Runs in O(1)."
- Most important to document in Zig: who owns which memory.

## The linked list

A doubly linked list of `i32`, plus a generic `Node(T)` I experimented with.

```zig
const IntNode = struct {
    value: i32,
    next_ptr: ?*IntNode,
    previous_ptr: ?*IntNode,
};

pub const IntLinkedList = struct {
    head: *IntNode,
    allocator: std.mem.Allocator,

    pub fn new(allocator: std.mem.Allocator, val: i32) !IntLinkedList { ... }
    pub fn search(self: *IntLinkedList, search_val: i32) ?*IntNode { ... }  // O(n)
    pub fn insert(self: *IntLinkedList, node: *IntNode, insert_val: i32) !void { ... }  // after `node`, O(1)
    pub fn delete(self: *IntLinkedList, node: *IntNode) void { ... }  // TODO
};
```

- Generics are functions that return a type: `fn Node(comptime T: type) type { return struct { ... }; }`.
  Inside, `@This()` refers to the struct being returned.
- The list stores the allocator it was created with and uses it for every node.
- Tests currently use `std.heap.ArenaAllocator` because there's no `deinit` yet.
  The arena frees everything at the end of the test but also hides leaks.

## Interfaces: the dictionary

Skiena defines a dictionary as anything supporting search, insert and delete.
Zig has no traits or interfaces. There are two standard patterns instead:

| Pattern | Rust equivalent | How it works |
|---|---|---|
| Struct of function pointers ("vtable") | `dyn Trait` | A type-erased pointer plus a table of function pointers. `std.mem.Allocator` works this way. |
| Compile-time duck typing (`anytype`) | Generics with trait bounds | Compiles for any type with the right methods; a missing method is a compile error. |

I used the vtable pattern so the backend can be swapped at runtime:

```zig
pub const IntDictionary = struct {
    ptr: *anyopaque,
    vtable: *const VTable,

    pub const VTable = struct {
        search: *const fn (ptr: *anyopaque, value: i32) bool,
        insert: *const fn (ptr: *anyopaque, value: i32) std.mem.Allocator.Error!void,
        delete: *const fn (ptr: *anyopaque, value: i32) bool,
    };

    pub fn search(self: IntDictionary, value: i32) bool {
        return self.vtable.search(self.ptr, value);
    }
    // insert and delete forward the same way
};

pub fn fromIntLinkedList(list: *IntLinkedList) IntDictionary {
    return .{ .ptr = list, .vtable = &int_linked_list_vtable };
}

fn intLinkedListSearch(ptr: *anyopaque, value: i32) bool {
    const list: *IntLinkedList = @ptrCast(@alignCast(ptr));
    return list.search(value) != null;
}
```

How the pieces map to Rust:

| Rust | Zig |
|---|---|
| `trait Dictionary { ... }` | `VTable`, the list of required functions |
| `&mut dyn Dictionary` (data pointer + vtable pointer) | `IntDictionary` |
| `impl Dictionary for IntLinkedList` | `int_linked_list_vtable` plus the `intLinkedList…` functions |
| `&mut list as &mut dyn Dictionary` | `fromIntLinkedList(&list)` |

Differences from Rust:

- I write the vtable myself; Rust's compiler generates it.
- Turning `*anyopaque` back into `*IntLinkedList` is unchecked. Pairing the
  wrong pointer with a vtable compiles and misbehaves at runtime.
- Leaving a field out of the vtable is a compile error, so all three functions
  must be provided.
- Methods on `IntDictionary` that aren't in the vtable work like default trait
  methods: every backend gets them. `std.mem.Allocator` builds `create`,
  `alloc` and `free` on top of a few raw vtable functions this way.
- The dictionary borrows the list; it doesn't own or free it.
